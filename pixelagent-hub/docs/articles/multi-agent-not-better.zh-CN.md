# 我让 4 个 AI Agent 分工写代码，测了 30 次，结果并不比 1 个强

> 项目地址：https://github.com/Jiarong-Song233/PIXELAGENT-HUB
>
> 在线体验（不需要注册，也不需要后端）：https://jiarong-song233.github.io/PIXELAGENT-HUB/

## 起因

"多 Agent 协作"是这两年最热的词之一：一个 Agent 规划、一个写码、一个测试，听上去就像一支开发小队。我做了一个像素风的版本，叫 PixelAgent Hub。它有四个角色：

- **Manager**：拆解需求；
- **Coder**：写一个离线的 HTML/CSS/JS 小应用；
- **Builder**：用 esbuild 真实编译；
- **Tester**：写检查清单，然后在沙箱浏览器里逐项点击、输入、断言。

编译错误和失败的检查会作为证据交回 Coder 返修。

做出来之后，我想回答一个很朴素的问题：**多出来的那个"规划"Agent，到底有没有用？**

## 实验怎么做的

我选了 5 个固定的小应用：计数器、待办清单、计算器、温度转换器和两道题的小测验。每个应用的需求里都写死了元素 ID 和行为，检查清单也是固定的，同一个应用无论用哪种策略生成，都按同一组标准验收。

两种策略：

- **先规划再写码**：Manager → Coder；
- **直接写码**：只有 Coder。

每种策略、每个应用各跑 3 次，一共 30 次真实生成，模型是 `deepseek-v4-pro`。所有生成都在同一个干净的提交上完成，源码、事件日志、检查计划、浏览器报告和截图全部提交进仓库，任何人都可以核对。

## 结果

| 策略 | 构建成功 | 浏览器检查全部通过 | 中位耗时 | 平均 token |
| --- | ---: | ---: | ---: | ---: |
| 先规划再写码 | 14/15 | **13/15** | 125 s | 9,604 |
| 直接写码 | 14/15 | **12/15** | 119 s | 8,390 |

**相差 1 次，3 次重复根本无法区分这种差距。** 规划平均每个应用多花了约 1,200 token，速度也没有更快。

更让我意外的是：完成构建的 28 次生成，**全部第一次就编译通过**。我精心设计的"编译失败 → 返修"循环，在真实模型上一次都没触发。

## 那 5 次失败是什么

每一次失败我都逐条看过：

1. **两次超时**：两种策略各有一次，Coder 超过了 180 秒的固定上限。
2. **小测验计分不变**：答对答错，分数都停在 0。这是真实的功能缺陷。
3. **两个温度转换器用了 `type="number"`**：需求明确写的是"文本输入框"。检查要输入 `abc` 验证错误提示，但数字输入框根本输不进去。这两次都来自"直接写码"组。

注意第 3 条：如果只让 Agent 自己汇报"完成了"，这两个应用都会被当成成功。**真正把问题揪出来的，不是分工，而是验证。**

## 第二个意外：测试员也会写错

后来我又让小队生成了 6 个更花哨的应用：贪吃蛇、番茄钟、小费计算器、像素宠物、翻牌配对和配色生成器。其中番茄钟第一次只过了 5/10，可截图里的计时器明明运行正常。

查下去才发现，**错的是 Tester 写的检查计划**：所有检查在同一个页面上顺序执行，第 5 项点了 Start 并确认它变成禁用，第 6 到 10 项又都从"点 Start"开始。按钮已经禁用，自然点不动。

后来我在浏览器里做在线生成时又撞上了同一个问题：一个"专注 / 休息"切换按钮，前一项检查切过去了，后一项再切一次又切回来。连续两次生成，应用都是对的，检查却都失败（中间还有一次是 Coder 自己出错）；更糟的是，失败还会触发一轮白费的返修。

修法是测试工程里最基本的一条：**每项检查都从一个刚加载的页面开始**。改完之后再跑同样的需求，3 次里有 2 次 10/10 全部通过。

## 第三个意外：真正的瓶颈是"测试员"

把整个流程搬进浏览器之后，我用访客的方式又测了一遍：在真实的网页里，用 `deepseek-chat` 跑同样 5 个固定用例，每个 3 次。

第一轮只有 **8/15** 完整通过。我逐个翻失败记录，结论出乎意料：**没有一次是应用本身写错了，全是 Tester 写的检查有问题。**

- 计算器的减法检查从头到尾没选运算符，应用按默认的加法算出 3 + 10 = 13，检查却期望 −7。
- 温度转换器的检查想用"点击"去切换下拉框，可点击并不会改变下拉框的值。
- 计数器的检查自己算错了数：+1 +1 −1 +1 −1 −1 −1 明明等于 −1，它却写 −2。
- 测验的检查没先选答案就点"下一题"，而"下一题"在答题前本来就是锁定的。

更讽刺的是，失败会触发返修：Coder 被叫回去，修改一个本来就没问题的应用，当然修不好。

我做了几件事：

1. **改 Tester 的提示**：要求每一项检查自己设好依赖的每个输入框和下拉框，并说清楚下拉框该怎么选。
2. **补检查语言的短板**：新增"是否可见"的断言，因为隐藏元素里的文字其实还在；文字比较改成"页面上显示的文字或源码里的文字任一对上就算"。
3. **让 Tester 先复查自己**：检查失败时，Tester 先判断是检查写错了还是应用真有问题；写错的检查纠正后重跑，只有确认是应用的问题才交给 Coder。

固定用例的完整通过从 8/15 提高到 11/15，再到 14/15。

接着我换了 6 个更难的想法：贪吃蛇、番茄钟、像素宠物、翻牌配对、配色生成器和小费计算器。这一轮又发现一个尴尬的事实：**我写的"复查"功能，在 8 次真实运行里有 7 次因为模型输出的格式不合规被整体丢弃了，等于从来没真正工作过。** 单元测试之所以全过，是因为我喂给它的都是格式标准的回复。

把解析改成"逐条校验、坏一条丢一条"之后，这 6 个想法的完整通过从 7/18 → 9/18 → **11/18**。过程中我还亲手引入、又修掉了一个回归：改用"显示出来的文字"之后，按钮上的 CSS 大写让"Pause"变成了"PAUSE"，三个番茄钟一起挂掉。

这一段我学到的是：

- **多 Agent 系统里最容易被忽视的，是负责验收的那个 Agent。** 它也是模型，也会算错、也会漏步骤，而它的错会被当成别人的错去"修"。
- **只用"干净的输入"测 LLM 管线，测出来的是假象。** 必须用真实模型、真实页面跑过，才知道它到底能不能工作。
- **能说清楚"这一轮没测到什么"，和测到了什么一样重要。** 报告里每个数字都附带了原始记录，包括那些不好看的。

## 第四个意外：应用早就是对的，是检查"看不见"

11/18 之后，我没急着改提示词，而是先把剩下 7 次失败逐个复盘：把每次的检查计划拿回保存下来的源码上重放，不调模型、不花钱。结论是 **7 次里没有一次是应用第一次就写错了**：

- 5 次是检查语言**表达不了**需求。"棋盘上有 16 张牌"需要数元素个数，"饥饿值进度条是 90"需要读 `aria-valuenow` 属性，可检查当时只会比较一个元素的文字。
- 1 次是检查用的 iframe 被浏览器**节流**了：它放在屏幕外又设成了隐藏，于是 CSS 过渡永远播不完，定时器一秒才跑一次。检查看到的，和访客看到的根本不是同一个应用。
- 更糟的是，返修轮把其中 2 个本来正确的应用"修"坏了：Coder 被要求修复一个任何改动都满足不了的检查，只好乱改。

于是我给检查语言加上了"数个数"（`count`）和"读属性"（`attribute`），并把检查 iframe 挪进视口，改成透明、不拦截点击。再跑 18 次，结果是 **12/18**，离我预测的 17/18 差得远。

翻记录才发现：三个贪吃蛇这次都用 `opacity: 0` 来隐藏遮罩层。人眼看它已经消失了，但我的 `visible` 照搬了 Playwright 的规则，只要元素有尺寸、没设 `visibility:hidden` 就算"可见"。上一轮的贪吃蛇碰巧用的是 `visibility`，所以没暴露。

把规则改成"它自己或任一祖先完全透明就算隐藏"之后，第五轮达到 **17/18**，三个贪吃蛇全部通过。这一轮没有一条检查被丢弃，也就是说，提升不是靠少检查换来的。

## 第五个意外：换一批没见过的想法，分数立刻掉下来

到这一步，我开始怀疑自己：这 6 个想法已经被我反复用来调了好几轮，17/18 会不会只是"背熟了考卷"？

于是我换了一种测法：每一轮另写 8 个全新的想法（骰子、井字棋、密码生成器……），**先提交到仓库，再运行**，而且它们从不参与修正。上一轮暴露的问题拿来修，修完之后，只在下一批从没见过的想法上评分。

第一批的结果很说明问题：在 6 个熟悉的想法上能拿 16/18，换成没见过的想法，只有 10/16。确实有过拟合。

接下来三轮，每一轮都换一批没见过的想法。按"全部检查通过、且一条检查都没丢"的严格口径，结果是 **10/16 → 12/16 → 14/16**。这几轮修的东西依然都在"检查"这一侧：

- 单选框只改了 value，没有真的选中；
- 进度条要读的是 `style.width`，而不是整个 style 属性；
- 计时器暂停后，要能检查它"保持不动"；
- 模型输出被 DeepSeek 默认的 4096 token 上限截断。

还有一个改动，让我对"让模型自己复查"有了新认识。复查者常常在理由里写"这条检查少点了一步"，结论却判"应用错"。我先把输出格式改成先写理由、再下结论，有所好转，但没有根治。最后的办法是**不再让它下结论**：它只回答一个事实问题——"一个完全满足需求的应用，能不能通过这条检查？"结论由代码根据这个回答推出。这之后，"理由和结论自相矛盾"的情况就消失了。

剩下的失败里，开始出现检查抓到的**真实应用 bug**：CSS 把 `hidden` 属性覆盖了，导致结果面板关不掉；贷款总额差了 4 分钱；$27.775 被舍成了 $27.77。这正是检查本该做的事。

回头看，这 6 个想法从 7/18 一路走到 17/18，除了"模型回复格式错了就退回重写"这一条，**没有一处改动碰过应用是怎么写的**。每一次提升都来自让检查看到人看到的东西、说出需求真正的意思。

## 我的结论

- **对这种规模的任务，规划 Agent 的价值没有测出来。** 它也许在更大的项目上有用，但不能靠直觉认定。
- **验证比分工重要得多。** 编译器和真实浏览器不会被"我已经完成了"骗过去。
- **检查者本身也需要被检查。** 模型写的测试同样会出错，失败证据要能追溯到具体的选择器、期望值和实际值，否则你修的可能根本不是那个问题。
- **把不讨好的结果也公开出来。** 这比一个漂亮的成功率更有说服力。

## 现在你可以自己试

我最后把整个流程搬进了浏览器：打开在线页面，点 **BUILD LIVE**，填入你自己的 key（支持 DeepSeek、Claude、OpenAI、通义千问、智谱、OpenRouter、硅基流动，也可以连你本机的 Ollama 或 LM Studio），四个 Agent 就会在你的标签页里现场写一个应用。

- 模型请求从你的浏览器直连提供商，key 默认只保存在当前标签页；
- 代码用 esbuild-wasm 编译，检查在沙箱 iframe 里逐项执行；
- 检查失败时，Coder 会获得一次返修机会。

用 `deepseek-chat` 生成一个番茄钟，大约 20 秒。

界面是像素风的，每一个动画都对应一条真实事件：红线亮起来，就是真的有一个错误正在被交回给 Coder。
