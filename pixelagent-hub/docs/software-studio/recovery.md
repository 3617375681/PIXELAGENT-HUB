# 本地任务持久化与重启

Records API 启动时读取 `<RECORDS_ROOT>/runtime-jobs.json`，将遗留的 `queued` / `running` 任务标记为 `failed`，错误为 `Recovered after process restart`。成功、失败和取消的历史保持原状；不会自动重复付费模型请求。恢复时的 `finishedAt` 表示服务器确认中断的时间，不能用于推断进程实际停止时间。

Studio 项目读取时与恢复后的任务状态同步。已成功构建的项目仍从原目录加载源码、预览、诊断、版本和人工决定。失败或取消后可点击“重新生成新版本（调用模型）”，或调用 `POST /api/studio/projects/:projectId/retry`（空对象）。此操作从头执行，沿用原需求、修改历史和返修上下文，生成新项目与任务并通过 `retry.parentProjectId` 关联原记录；原错误不被覆盖，不继承人工批准，不自动选择新版本。首次作品失败时 `selectedProjectId` 为 `null`，构建成功后由用户选择候选版本。

重试受原有认证、创建限流和队列约束，正在停止的任务不能重试；模型调用会产生新用量。当前不支持从中断的模型调用或执行阶段继续，也不会在刷新或服务重启时自动重试。新记录保留 `stoppedPhase`，界面显示已停止的阶段；旧记录依据已有角色结果显示失败位置。

任务历史通过临时文件和原子替换保存，同一进程中对同一路径的写入串行执行，保存入队时固定快照。不要让多个 API 进程共享同一记录目录；该机制不提供跨进程锁或事务，也不替代备份。

队列容量用尽时，请求会返回原有 `QUEUE_FULL` 错误，拒绝任务持久化为失败，尝试次数仍为零，并释放任务占用。容量恢复后可重新提交同一任务；不会因遗留“排队中”记录永久阻止重试。回归测试实际占满运行位与排队位，验证拒绝工作未被执行、失败状态重启后保留及再次提交成功。

只有文件不存在时才初始化空历史。无效 JSON、错误的顶层结构、重复任务 ID 或无效状态/时间会导致初始化失败，原文件保留。遇到此类错误时：

1. 停止使用该记录目录的 API，备份整个目录。
2. 检查 `runtime-jobs.json`，优先从已知完整备份恢复；不要直接删除项目或覆盖历史。
3. 若选择新建记录目录，用 `RECORDS_ROOT_OVERRIDE` 指向新位置，保留旧目录供检查。

自动测试覆盖排队/运行状态恢复、终态和成功结果保留、24 个并发任务持久化、损坏文件保留，以及独立工作进程开始执行后被强制终止再恢复。运行：

```powershell
npx tsx --test src/web/runRuntime.test.ts
npx tsx --test src/web/server.restart.test.ts
```

HTTP 重启测试在独立进程中启动完整 Records 服务栈，使用本地模型响应夹具完成一个项目，再于另一个项目等待响应时强制终止进程。重启后验证成功作品的预览、ZIP、诊断和版本选择保留，中断任务明确失败，队列为空，模型请求没有重复。这是受控传输与恢复测试，不是模型质量验收。

Windows 原子替换遇到读取句柄短暂占用时最多重试五次，仍失败则保留错误。跨平台断电、磁盘满和自动继续执行仍需单独验证。
